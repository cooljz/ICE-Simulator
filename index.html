    Candidate types

    A candidate is a transport address (IP, port, protocol) where a peer might receive packets. ICE gathers four kinds and prefers the ones that skip middleboxes.

    host

    Local interface

    Obtained from
    The device's own network interfaces.
    Works when
    Both peers share a LAN, or one has a public address.
    Type preference
    126
    srflx

    Server reflexive

    Obtained from

    Works when
    The NATs allow hole punching. Fails when both are symmetric.

    Obtained from

    Almost always. The peer sends to the TURN server, which forwards from the relayed address. Costs latency and server bandwidth.

    The algorithm, step by step

    1. Gather

      Each peer lists its host addresses, asks a STUN server for its server-reflexive address (a STUN Binding request, answered with the address the server saw) and asks a TURN server for a relayed address. With trickle ICE, candidates are sent as they appear instead of after gathering ends.

    2. Exchange

      Peers swap candidates, a username fragment and a password through signaling (in WebRTC, the SDP offer and answer). ICE does not define the signaling channel.

    3. Pair and prioritize

      Each peer pairs every local candidate with every remote candidate. Pairs whose local side is server-reflexive are pruned, because the packet would leave from the same host base as the host pair. The rest are sorted by pair priority.

    4. Check connectivity

      Each peer sends a connectivity check for every pair, in list order, paced at one every Ta (50 ms by default). A check is an ordinary STUN Binding request, the same message used to ask a STUN server for a reflexive address, but sent peer to peer: every ICE agent is both a STUN client and a STUN server. It carries the peers' username fragments, a message integrity check and ICE attributes (PRIORITY, ICE-CONTROLLING or ICE-CONTROLLED, USE-CANDIDATE). The success response echoes the source address the request arrived from. That proves the path works in both directions and reveals peer-reflexive addresses. For a relay candidate, the agent hands the request to the TURN server, which sends it from the relayed address. Both peers check at once, which is what opens the NAT holes. Pairs that share a foundation start Frozen and thaw when a sibling succeeds.

    5. Nominate

      The controlling agent picks one valid pair and repeats the check with the USE-CANDIDATE attribute. The controlled agent confirms. That pair carries the media.

    6. Keep alive

      Consent freshness checks run for the life of the session. If the selected path dies, or the network changes, an ICE restart builds a new checklist.

    Why both peers check at the same time

    A restricted NAT drops inbound packets from addresses its inside host has not contacted yet. So Alice's first check toward Bob's public address is dropped by Bob's NAT. Sending it still creates a mapping on Alice's NAT that now admits packets from Bob's address.

    Bob runs the mirror checklist at the same moment and sends a check toward Alice's public address. That packet finds the hole Alice just opened and is delivered. Alice answers it, and Bob's own hole is open too, so Alice's retransmitted check now gets through. Each outgoing check opens the hole the other side's check needs. Neither order of arrival matters, as long as both sides keep sending.

    The simulator lists only Alice's checklist and does not model timers. It marks a pair as succeeded when the NAT types allow this exchange, and the event log notes Bob's mirror check next to each of Alice's.

    t0  Alice → Bob's srflx
    Alice's NAT: new mapping, allows Bob's IP
    Bob's NAT:   no entry for Alice, dropped
t0  Bob → Alice's srflx
    Bob's NAT:   new mapping, allows Alice's IP
    Alice's NAT: Bob's IP allowed, delivered
    Alice replies; her response passes Bob's hole
t1  Alice retransmits her check
    Bob's NAT:   now allows Alice, delivered
    Bob replies. Both pairs are valid.

    A symmetric NAT breaks this: it opens a new mapping per destination, so the port that STUN reported is not the one used toward the peer.

    Priority arithmetic

    Every candidate gets a 32-bit priority built from three parts:

    priority = 2^24 × type_pref
         + 2^8  × local_pref
         + (256 − component_id)

    With one interface (local preference 65535) and one component (RTP, id 1):

    host   126 → 2130706431
prflx  110 → 1862270975
srflx  100 → 1694498815
relay    0 →   16777215

    A pair's priority combines the controlling agent's value G and the controlled agent's value D:

    pair = 2^32 × MIN(G, D)
     + 2   × MAX(G, D)
     + (G > D ? 1 : 0)

    The smaller candidate dominates, so a pair is only as good as its weaker half. A host–relay pair ranks below a srflx–srflx pair. MAX breaks ties, and the last term makes both peers sort identical lists even though G and D swap roles.

    Foundations

    A foundation is a short opaque string. Two candidates get the same foundation when they have the same type, the same base address, the same transport protocol and were obtained from the same STUN or TURN server. Such candidates usually behave the same way in the network.

    A pair's foundation is the local foundation joined to the remote foundation. It drives the freezing rule: for each pair foundation, only the best pair starts Waiting. The others stay Frozen and thaw when a pair with that foundation succeeds. If it succeeded, its siblings probably work too, and if it failed, they would probably fail the same way, so the agent does not spend checks on them first.

    In the simulator each peer has one interface, so every pair ends up with a distinct foundation and nothing starts Frozen. Freezing matters with several interfaces or several candidates from the same server, where it keeps the checklist short.

    Alice host   192.168.1.23:54321  F1
Alice srflx  203.0.113.7:61002   F2
Alice relay  192.0.2.50:49152    F3
Bob   host   10.0.0.8:49170      F4

pair (Alice host, Bob host)  F1/F4
pair (Alice srflx, Bob host) F2/F4

    The candidate lists above the checklist show each candidate's foundation next to its priority. The SDP line in the next sections carries it as the first field after a=candidate:.

    Pair states

    Frozen
    Not checked yet. It waits for another pair with the same foundation to succeed, so the peers do not repeat the same NAT probe.
    Waiting
    Ready. The next Ta tick will start its check.
    In progress
    A Binding request is on the wire.
    Succeeded
    The response arrived. The pair joins the valid list.
    Failed
    Timeout or error response. The pair is never retried in this round.

    Frozen pairs exist because of foundations. See Foundations.

    Roles and nomination

    One peer is the controlling agent (normally the offerer) and the other is controlled. Only the controlling agent chooses the final pair. If both claim the same role, the 487 error response and a random tie-breaker value resolve it.

    An ICE-lite agent, such as a media server with a public address, only answers checks and is always controlled.

    Regular nomination lets checks finish, then nominates the best valid pair. It gives the best path and takes longer.

    Aggressive nomination sets USE-CANDIDATE on every request, so the first success is chosen. Media can start sooner, but a better pair may never get its turn. Try both in the simulator with the Full cone ↔ Symmetric scenario.

    Beyond the basics

    Trickle ICE

    Sends candidates one by one over signaling and starts checking right away. Connection time drops from "slowest gather" to "first working pair".

    ICE restart

    New username fragment and password, new gathering, new checklist. Used when the path fails or the device changes networks, for example Wi-Fi to cellular.

    Why symmetric NATs hurt

    A symmetric NAT creates a new mapping for every destination. The port a STUN server saw is useless for the peer. Two symmetric NATs, or symmetric plus port-restricted, cannot punch through and need TURN.

    Cost of relay

    Relayed media adds a hop and uses the provider's bandwidth. It is the fallback that makes ICE succeed nearly every time.
